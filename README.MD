# Azure IaC Module Library

## Scope

Four reusable Terraform modules for Azure: a resource group and networking foundation (VNet,
subnets, NSGs), an AKS cluster, an Azure SQL Database, and a Key Vault. `examples/integration/`
composes all four together against a real remote state backend. Scope is deliberately limited to
these four modules — anything beyond this list requires a reason, written down, before it
gets added.

## Status

All four modules are built, and — as of a full end-to-end deploy on 2026-09-20 — proven: real
infrastructure, actually created in Azure, actually torn down afterward, not just `terraform plan`
output. `examples/integration/` is a permanent, checked-in composition of all four modules against
the project's real remote backend (verified via `terraform plan`, not yet applied as a permanent
environment). CI runs on every push (`terraform fmt`/`validate`/`tflint`, Trivy, GuardLine) and has
already caught and driven fixes for 18 real misconfigurations. See `CHALLENGES.md` for the full,
honest log of what was fixed, what was deliberately deferred, and why.

## Why this project

- First hands-on infrastructure-as-code project, distinct from [GuardLine](#) (application/tooling
  security scanner, shipped).
- Feeds directly into a later GitOps pipeline project, which will consume these modules.
- The Key Vault module is a deliberate callback to GuardLine's secrets-detection scanner: the
  database module's admin password is generated by Terraform, never typed by a human, and stored
  as an actual Key Vault secret — read only by the one identity (AKS's managed identity)
  explicitly granted a narrow, read-only RBAC role to access it. This is the pattern GuardLine's
  findings tell people to use instead of hardcoding credentials, actually built and verified.

## What's actually demonstrated here

- **A real, verified deploy.** All four modules composed and applied together in Azure, an AKS cluster running, a SQL database    
  provisioned, a Key Vault secret stored and
  read by the correct, narrowly-scoped identity. See `CHALLENGES.md` for the debugging story
  (region cascades, RBAC least-privilege regressions caught and fixed, a data-plane-vs-management-
  plane permissions issue hit twice on two different resources) rather than a sanitized summary.
- **A working CI pipeline that actually finds things.** Not a pipeline that passes trivially —
  Trivy's first scan surfaced 18 findings across every module; 9 were fixed, 9 were
  deliberately deferred with written reasoning, all tracked in `CHALLENGES.md`.
- **Least-privilege access control, implemented and independently verified.** Two separate RBAC
  role assignments on the Key Vault (a narrow "Secrets User" role for AKS's identity, a broader
  "Secrets Officer" role for the identity running Terraform) — including one instance where these
  got accidentally collapsed into one role under debugging pressure, caught by checking the portal
  directly, and fixed.
- **Secrets that are generated, not typed.** The database module's admin password is created by
  Terraform's `random_password` resource and never appears in any file, `.tfvars`, or human-typed
  string, anywhere in the project.

## Tooling decisions

| Decision | Choice | Details |
|---|---|---|
| IaC tool | Terraform | See [`docs/adr/0001-terraform-vs-bicep.md`](docs/adr/0001-terraform-vs-bicep.md) |
| State backend | Azure Storage (remote, with locking) | Bootstrapped via a small, local-state-only config in `bootstrap/` — see that folder's README |
| CI validation | `terraform fmt`, `terraform validate`, `tflint` | Runs on every push/PR |
| IaC security scanning | [Trivy](https://github.com/aquasecurity/trivy) | Scans Terraform for infrastructure misconfigurations; findings published to GitHub's Security tab |
| Pipeline security scanning | [GuardLine](#) | Scans `.github/workflows/*.yml` for pipeline-level misconfigurations — a different layer than Trivy, not a duplicate of it |
| Resource naming | Microsoft Cloud Adoption Framework pattern: `{type}-{workload}-{environment}-{region}-{instance}` | e.g. `rg-iacmods-dev-eus-001`. Key Vault uses a Terraform-generated random suffix instead of a fixed instance number, for global-uniqueness reasons — see `modules/key-vault/README.md` |

## Repo structure

```
azure-iac-modules/
├── bootstrap/              # One-time setup: creates the remote state storage account (local state, intentionally)
├── modules/
│   ├── networking/         # Resource group, VNet, subnets, NSGs
│   ├── aks/                # AKS cluster with a system-assigned managed identity
│   ├── database/           # Azure SQL Database, admin password generated by Terraform
│   └── key-vault/          # Key Vault, RBAC-scoped access for AKS's identity
├── examples/
│   └── integration/        # Real, checked-in composition of all four modules against the remote backend
├── docs/
│   └── adr/                # Architecture Decision Records
├── .github/workflows/      # CI: fmt, validate, tflint, Trivy, GuardLine
└── CHALLENGES.md           # Full, honest log of decisions, bugs, and deferred work
```

## Known, deliberately deferred items

Tracked in detail in `CHALLENGES.md`, not silently skipped: AKS API server authorized IP ranges,
AKS private cluster mode, the Azure Policy add-on, an AKS disk encryption set, and SQL Server
extended auditing (needs a dedicated audit-log storage account). Each requires meaningfully more
infrastructure or operational complexity than a portfolio-scope hardening pass covers, and each
has a written reason for the deferral rather than an unexplained gap.
